\section{Review of code used to generate positive and negative control
heatmaps in Figure 3DE of
Martino}\label{review-of-code-used-to-generate-positive-and-negative-control-heatmaps-in-figure-3de-of-martino}

Review of the code in
\href{https://github.com/SchlossLab/Schloss_RPCA_XXXXXX_2024/blob/main/deicode_benchmarking/simulations/negative_control.ipynb}{\texttt{deicode\_benchmarking/simulations/negative\_control.ipynb}}
reveals two important problems with the generation Martino's Figure 3DE.
For background, the \texttt{X\_random} and \texttt{X\_signal} matrices
represented the negative and positive controls, respectively, that were
generated in an earlier block of this notebook. For both matrices, there
were 1000 rows for each feature or taxon and 200 columns for each
sample. At L13 and L15 of block 183, the
\href{https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.imshow.html}{\texttt{imshow}
function} from the pyplot package within the \texttt{matplotlib} Python
library is used to generate heatmaps of the two matrices.

\normalsize\setstretch{1.75}

Within the arguments to \texttt{imshow}, the matrices are transformed by
adding 1 to each cell and then subjecting the matrices to a central log
ratio transformation with the
\href{https://scikit.bio/docs/dev/generated/skbio.stats.composition.clr.html\#skbio.stats.composition.clr}{\texttt{clr}
function} from the composition statistics module of the \texttt{skbio}
Python library. It is important to note that the \texttt{clr} function
assumes that the rows represent compositions or samples and the columns
represent the components or taxa. Therefore, \texttt{X\_random} and
\texttt{X\_signal} should have been transposed prior to performing the
clr transformation. For example, earlier at L2 and L6 of the same code
block, the matrices were transposed prior to using the \texttt{rclr}
function.

As executed in the notebook, the result of using the \texttt{clr}
function was the same shape as the input matrices with features as rows
and samples as columns. The transformed data were then used in the
\texttt{imshow} function which plots the rows and columns of the matrix
to the rows and columns of the heatmap. However, later at L21-24 in the
same code block, ``Samples'' is added to the y-axis label and
``Features'' is added to the x-axis label, which is the reverse of the
actual situation. These problems hid the fact that samples rather than
taxa were shared between the treatment groups. Of course, sharing
samples between treatment groups does not make sense and the taxa
instead should have been shared.

\section{\texorpdfstring{Review of \texttt{build\_block\_model} function
and its
dependencies}{Review of build\_block\_model function and its dependencies}}\label{review-of-build_block_model-function-and-its-dependencies}

Because it was clear that there was a problem in the simulation code
such that samples rather than taxa were shared between treatment groups,
I reviewed the code in
\href{https://github.com/SchlossLab/Schloss_RPCA_XXXXXX_2024/blob/main/deicode_benchmarking/simulations/scripts/simulations.py\#L175}{\texttt{build\_block\_model}}
and related functions to better diagnose the problems in the simulation.
The \texttt{build\_block\_model} function can be found in
\href{https://github.com/SchlossLab/Schloss_RPCA_XXXXXX_2024/blob/main/deicode_benchmarking/simulations/scripts/simulations.py}{\texttt{deicode\_benchmarking/simulations/scripts/simulations.py}}.
The function is called in
\texttt{deicode\_benchmarking/simulations/negative\_control.ipynb} to
generate the positive control data in Figure 3D and in
\texttt{deicode\_benchmarking/simulations/scripts/cluster\_build.py} to
generate the overlapping data analyzed in Martino's Figure 3ABC. The
\texttt{build\_block\_model} function is listed below except for lines
corresponding to comments (L185-236) and code that did not impact the
generation of \texttt{X\_noise} (L244-253 and L262-267). The function
returned the values of \texttt{X\_true} and \texttt{X\_noise}.

As called in \texttt{cluster\_build.py}, the value of \texttt{rank} was
2 (i.e., the number of treatment groups), \texttt{num\_samples} was 200
(i.e., the number of samples across all treatment groups),
\texttt{num\_features} was 1000 (i.e., number of taxa or features), and
\texttt{overlap} was 20 (i.e., the number of features that overlapped
between the treatment groups; it was zero in the positive control
analysis). The values of \texttt{spar}, \texttt{C\_}, \texttt{hoced},
and \texttt{hsced} were based on a parameter that was altered for each
sequencing depth. The \texttt{spar} and \texttt{C\_} values were set to
the same value (e.g., 2500) and were used to scale the relative
abundance values in the \texttt{Subsample} (L261) and
\texttt{block\_diagonal\_gaus} (L237-243) functions, respectively. As
used in the simulations with partially overlapping features the
\texttt{hoced} and \texttt{hsced} values were set to \texttt{hoced} and
\texttt{hsced} values divided by 15; for the positive control analysis
they were divided by 60. These values were used in the
\texttt{Homoscedastic} (L257) and \texttt{Heteroscedastic} (L259)
functions where \texttt{hoced} and \texttt{hsced} were used to set the
standard deviation of a normal distribution with mean set to the
relative abundance of the sample-taxon pair receiving additional noise
uniformly or randomly. The values of \texttt{spar}, \texttt{C\_},
\texttt{hoced}, and \texttt{hsced} that were used in
\texttt{build\_block\_model} were selected by fitting the model to
experimental data from a study comparing the microbial communities on
subject's fingers and keyboards. Although I did not attempt to replicate
their model fitting, other code is found in \texttt{simulations.py} that
ostensibly performs this analysis.

A general problem with the code in \texttt{simulations.py} was that if I
loaded \texttt{simulations.py} and ran \texttt{build\_block\_model}
multiple times with the same input data and random number generator
seed, the code did not produce the same results. Although not a critical
problem, the lack of computational reproducibility was part of my
motivation to assess the benchmarking test results with ten rather than
only one seed.

Finally, comments in \texttt{build\_block\_model} describe the function
as returning a data frame with \texttt{num\_samples} rows and
\texttt{num\_features} columns (L227-227). In fact, it returns a data
frame with \texttt{num\_features} rows and \texttt{num\_samples}
columns. This confusion might help explain why samples rather than
features overlap in the \texttt{block\_diagonal\_gaus} function as
written. This issue is described in the next section.

\subsection{\texorpdfstring{Review of \texttt{block\_diagonal\_gaus}
function}{Review of block\_diagonal\_gaus function}}\label{review-of-block_diagonal_gaus-function}

The function
\href{https://github.com/SchlossLab/Schloss_RPCA_XXXXXX_2024/blob/main/deicode_benchmarking/simulations/scripts/simulations.py\#73}{\texttt{block\_diagonal\_gaus}}
creates a model that describes the abundance of each taxon across the
samples for each treatment group before any noise has been applied to
the data. This function is called by \texttt{build\_block\_model} and is
also found in
\href{https://github.com/SchlossLab/Schloss_RPCA_XXXXXX_2024/blob/main/deicode_benchmarking/simulations/scripts/simulations.py}{\texttt{deicode\_benchmarking/simulations/scripts/simulations.py}}.

\setstretch{1.0}\footnotesize

\begin{Shaded}
\begin{Highlighting}[numbers=left,,firstnumber=73,]
\KeywordTok{def}\NormalTok{ block\_diagonal\_gaus(}
\NormalTok{        ncols,}
\NormalTok{        nrows,}
\NormalTok{        nblocks,}
\NormalTok{        overlap}\OperatorTok{=}\DecValTok{0}\NormalTok{,}
\NormalTok{        minval}\OperatorTok{=}\DecValTok{0}\NormalTok{,}
\NormalTok{        maxval}\OperatorTok{=}\FloatTok{1.0}\NormalTok{):}

\normalsize\setstretch{1.75}

As used in Martino, \texttt{ncols} was 200 and \texttt{nrows} was 1000.
As described in the Methods of the original study, the model uses a
normal distribution to vary the relative abundance of each taxa with
different distributions for each treatment group such that a specified
fraction of taxa overlapped between the two treatment groups. Within
\texttt{block\_diagonal\_gaus} the number of treatment groups was

\subsection{Summary}\label{summary}

Five problems were found in the code as written in the original
\texttt{simulations.py} script. They are listed here in order of
importance.

\textbf{1. Samples, not features, were shared between the two treatment
groups.} The intention was that features should be shared between
treatment groups, not samples.\\
\textbf{2. Among samples from the same treatment group, the abundance
distributions for each feature were uniform.} The result was that the
relative abundance for all features in the same sample and treatment
group had the same expected relative abundance. The intention was likely
that the abundance distribution within each sample varied by feature.\\
\textbf{3. The total number of individuals varied across each sample.}
Although there were claims that RPCA was insensitive to uneven sampling
effort, this was not actually demonstrated in Martino. It was necessary
for me to make the sampling effort uniform so this could be tested
\textbf{4. The heteroscedastic source of noise was actually applied to
all sample-taxon pairs.} The result was a second addition of noise to
all sample-taxon values rather than the intended subset of values.\\
\textbf{5. Negative mean values were used as the mean in normal
distribution sampling functions when calculating the heteroscedastic
noise.} It is likely that the intention was for negative values to be
transformed to zeros before sampling the distribution.\\
\textbf{6. The signs of negative values generated after applying the
heteroscedastic noise were made positive.} It is likely that the
intention was for negative values to be transformed to zeros.\\
\textbf{7. Setting the random number generator seed was inadequate to
ensure that rerunning \texttt{simulations.py} with the same parameters
yielded the same result.}

I suspect that the confusion over the information contained in the rows
and columns of the positive and negative controls was principally caused
by the first two problems listed in this summary. Taken together, these
problems do not entirely invalidate the claims made by Martino about the
performance of RPCA. Regardless, it was necessary to re-evaluate the
claims with revised code. Therefore, I rewrote \texttt{simulations.py}
as an R script \texttt{simulations.R} (found in
\texttt{workflow/scripts/}) that resolved the above-mentioned problems.

been used to train the model and 60\% would have been used to test the
model. Such a split would be curious since the training set is typically

multiple times to remove bias from the selection of the random number
generator seed.

Review of the code in both \texttt{negative\_control.ipynb} and
\texttt{cluster\_results.py} made it clear that only a single split of
the data was performed.

Finally, the choice of the number of neighbors (i.e., k) to use in the
KNN analysis was not described in the manuscript. Often the training set
will be repeatedly split to fit such hyperparameters
{[}\textbf{XXXXXX}{]}. As shown above in the code from box 186
\texttt{negative\_control.ipynb} at L10, a k value of 10 was used for
classifying the positive and negative control data. In contrast, as
shown above in the code from \texttt{cluster\_results.py} at L78, a k
value of 13 was selected for classifying the samples with overlapping
features.

In summary, the authors used inconsistent splits and k-values in their
simulations, misstated the nature of the split, did not incorporate
multiple splits, and provided no information for how the k-value was
selected. These problems raise the question of whether their models were
overfit (i.e., too small of a k value) or under fit (i.e., too large of
a k value). I implemented my own version of a KNN classifier
(\texttt{workflow/scripts/test\_train\_knn.R}) that allows users to
input a distance matrix, training, validation, and testing fractions,
and the number of iterations.

\subsection{Processing of case study
datasets}\label{processing-of-case-study-datasets}

After benchmarking RPCA using simulated data, Martino evaluated the
method relative to using Bray-Curtis and weighted UniFrac distances with
the Sponges and Sleep Apnea datasets {[}\textbf{XXXXX}{]}. Both datasets
consist of two treatment groups represented by varying numbers of
samples, each with a wide distribution in the number of sequences
(\textbf{Fig. XXXXX}). The datasets were analyzed separately by similar
methods. Before commenting on the analysis of these datasets, several
issues are noteworthy.

First, to create balanced experimental designs, with the authors
randomly selected an equal number of samples from each treatment group.
While unbalanced design is problematic for KNN classification, PERMANOVA
is not known to be sensitive to such designs. To mitigate the effects of
the random number generator seed, they repeated this sampling. The text
of the manuscript states that they performed ``10-fold random subsamples
of the data''. In fact, at L45 of
\texttt{deicode\_benchmarking/case\_studies/scripts/subsample.py} it is
clear that they only performed 9-fold random subsamples. Admittedly,
this is unlikely to have had a meaningful impact on the results of the
case study analysis

\subsection{PERMANOVA analysis of case study
datasets}\label{permanova-analysis-of-case-study-datasets}

The factors outlined in the previous section would likely impact the
results of Martino's PERMANOVA analysis of the case study datasets.
Several factors are worth raising and emphasizing.

First, throughout Martino's analysis, they report the PERMANOVA
F-statistic rather than the test's P-value. This is likely because there
was a pronounced effect size between the treatment groups in both
studies that was clearly evident in the first two axes of the
ordinations shown in Martino's Fig. 4EF. Reporting all tests as having
significant P-values regardless of the method used to calculate the
distance would not have been interesting. However, comparing
F-statistics is biased in favor of RPCA. This is because RPCA was run
using 2 (i.e., Sponges) or 3 (i.e., Sleep Apnea) axes and then used as
the basis for calculating the Euclidean distance between samples. The
analysis effectively removed higher ordered components thus dramatically
reducing the MSerror term in the denominator of the F-statistic
calculation. In contrast, Bray-Curtis and weighted UniFrac distances
were used without further processing in PERMANOVA leaving in the higher
ordered components. As done in my analysis, using datasets where the
first two axes for Bray-Curtis distances did not explain so much of the
variation would have provided a more balanced comparison of the methods.

Second, Martino did not show the variation across their 9 subsamplings
for their PERMANOVA or KNN classification analyses. This can be seen in
L43-72 of code block 104 from
\texttt{deicode\_benchmarking/case\_studies/case\_studies.ipynb}. An
illustrative example is shown here:

First, when describing their KNN analysis Martino again stated that they
performed 40:60 splits. As shown at L139 the test fraction was 0.4
rather than 0.6 as would have been expected from a 40:60 split. As
shown, Martino implemented a 60:40 split where 60\% of the data were
used to train the model an 40\% were used to test the model.

Second, inspection of the above code chunk demonstrates that they only
performed a single split of the data. Moreover, there was only one split
across all subsamples for each dataset. At L142 and L143 they assign the
output of the training-testing split from L138-141 to two variables,
\texttt{train\_index} (L142) and \texttt{test\_index} (L143). These
variables contain the indices for the samples in the training and
testing set across all the samples, stratified by the number of samples
in each treatment group (L140). It is important to note that the code
between L124 and L143 is only run once for each dataset creating a
single 60:40 split that is then used for each subsampling. On L155 and
L156, training and testing sets, respectively, are created for each
subsample based on the split that was performed at L138-L143. Because
the sample subsampling was not performed based on the 60:40 split,
different numbers samples from each treatment group appear in each of
the replicate subsamples. Thus, the training and testing sets were not
equally represented by both treatment groups. Considering KNN is
sensitive to unbalanced sampling designs, this would artificially
increase or decrease the accuracy of the classification. Finally, at
L163 to L169 it appears that KNN is run 10 times (i.e., see the
\texttt{range(11)} statement). However, the 10 values in \texttt{acc\_s}
are identical to each other. Furthermore, \texttt{acc\_s} is not used
outside the loop. At L171, the mean of \texttt{acc\_} is calculated;
however, \texttt{acc\_} is a single value. Regardless, because the
classifier does not use a random number generator seed, the ten values
in \texttt{acc\_s} would be identical to \texttt{acc\_} and of course
the mean of \texttt{acc\_}. For each dataset, subsampling, and iteration
of subsampling Martino should have split the data into a training and
testing split stratified by the treatment group. Also, these splits
should have been repeated many times (e.g., 10 or 100) with the mean
accuracy of those repeats returned as the mean accuracy for the
iteration of the subsampling for the dataset. The lack of replication or
balanced stratification of the treatment groups within the subsamples
significantly compromised the reliability of the KNN classification
accuracy results.

Martino subsetted the metadata data frame (i.e., \texttt{meta\_}) using
the values in the test data (i.e., \texttt{tmp\_test\_index}). Then they
used the \texttt{.shape} function to return the number of rows and
columns. The smaller number was then divided by 1.4 and converted to an
integer. There are several problems with this calculation. First, one
would expect the choice of k to be dependent on the number of samples
included in the \textbf{training} dataset and not the \textbf{testing}
dataset since its the observations in the training set that result in
the classification. Instead Martino subsetted \texttt{meta\_} by the
samples in the \textbf{testing} dataset. Furthermore, the number of
samples and not the amount of metadata for each sample that would be
relevant to determining the value of k. To illustrate this further, the
number of columns for the Sponges dataset was 46 and for the Sleep Apnea
dataset it was 50 (one column added for \texttt{y\_encode}). Therefore,
when more than 115 and 125 total samples, respectively, were in a
subsample k would hav been selected based on the number of columns in
\texttt{meta\_} (e.g.~46/0.4 = 114). These would have been the 150 and
158 subsamples for the Sponges datset and 150 and 184 subsamples for the
Sleep Apnea dataset. The values of k would have been 32 and 35 for these
subsamples in the Sponges and Sleep Apnea datasets, respectively. For
the other subsamples k would have been the total number of samples in
the subsample times 0.4 divided by 1.4. The subsamples with 70 samples
would have had a k value of 20 and the 110 subsamples would have had a k
value of 31. Because the stratification was not balanced (see above
discussion) these thresholds are approximate. For context, in the
simulations there were 200 samples with 120 in the training set and 80
in the testing set. A k of 13 was used. Therefore, the ratio of k to the
number of samples in the training set was 0.108333. Although no
justification was given for the k of 13, if the same ratio was used with
the case study datasets, the k values would have been 4, 7, 9, 10, and
12 for the subsamples of 70, 110, 150, 158, 185 samples, respectively
(e.g., 150 times 0.6 times 0.108333 = 9.75, converted to an integer
gives 9). As discussed above with the KNN analysis of the simulation
data, a preferred approach would have subdivided the training dataset
into a secondary training set and a validation datset. The secondary and
validation training sets could have been used to identify the optimal
value of k to use with the full training set on the testing dataset
{[}\textbf{XXXXXX}{]}. As described above with the discussion of the
choice of k for the simulation data, if a too small value of k is chosen
the model could be underfit to the data while too large of a value of k
could overfit the model to the data. Given the problems identified here,
it is clear that in practice there was no logic to the choice of k.
Therefore, it is difficult to have confidence in the reported accuracy
values from the KNN analysis.

Fourth, at L159 two dimensions from a principle coordinates analysis
(PCoA) performed on the Bray-Curtis and weighted UniFrac distances and
two dimensions from the RPCA were used to define the dataset for KNN;
this line would have ignored the third dimension from the Sleep Apnea
dataset and many dimensions from the PCoA. The KNN used a euclidean
distance to find the k nearest neighbors in the training dataset for
each value in the testing dataset. Because so much information was
censored from the Bray-Curtis and weighted UniFrac distances, those
methods were disadvantaged relative to RPCA. Considering a distance was
calculated by the \texttt{KNeighborsClassifier} function when called at
L165-166 it seems to be an odd choice to calculate a euclidean distance
on a distorted representation of the data rather than using the actual
Bray-Curtis or weighted UniFrac distances. Since
\texttt{KNeighborsClassifier} does not take distance matrices as input,
Martino could have at least used all of the dimensions for the
Bray-Curtis and weighted UniFrac distances to make a more fair
comparison to RPCA. Overall, the implementation of the KNN analysis was
biased towards favoring the RPCA approach. This was exacerbated by the
choice of datasets that had large differences between their treatment
groups.

secondary training and validation dataset. Furthermore, it also accepts
